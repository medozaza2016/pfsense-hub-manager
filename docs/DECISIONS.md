# Decision Log

This document records confirmed architectural decisions. Proposals and open questions must not be presented as settled.

## Confirmed decisions and constraints

### DEC-001, Multi-firewall product
**Status:** Accepted  
**Decision:** Build a centralized manager for multiple pfSense firewalls and locations. Do not hard-code exactly two devices.

### DEC-002, Edition support
**Status:** Accepted  
**Decision:** Target both pfSense Plus and pfSense CE. Treat endpoint and package compatibility as version-dependent and verify it per device.

### DEC-003, No Netgate Nexus dependency
**Status:** Accepted  
**Decision:** The product must remain independent of Netgate Nexus.

### DEC-004, Read-only first
**Status:** Accepted  
**Decision:** Initial integration is read-only. No configuration-changing API methods are enabled for the application at this stage.

**Status:** Verified for first Plus firewall  
**Decision:** Use a dedicated regular pfSense user named pfsense_hub, not an administrator account, for the initial API integration. The API key belongs to this user and the user has the eight GET privileges recorded in INTEGRATION-STATUS.md.

**Status:** Accepted  
**Decision:** Leave the existing 172.10.x.x addressing unchanged during current development.

### DEC-007, Defer second firewall connection
**Status:** Accepted

### DEC-008, Full management product direction
**Status:** Accepted  
**Decision:** The long-term product is a full pfSense management application, not a read-only monitoring dashboard. Delivery will be phased, with read-only first and write operations introduced only after security and recovery controls are implemented.

### DEC-009, Extensible firewall inventory
**Status:** Accepted  
**Decision:** The hub must support adding additional pfSense firewalls over time.

### DEC-010, Defer firewall connection method
**Status:** Deferred  
**Decision:** Do not select or implement the firewall-to-hub connection method yet. Keep the transport replaceable until a separate decision is made.

### DEC-011, Application deployment environment
**Status:** Accepted  
**Decision:** Deploy pfSense Hub Manager on the existing Proxmox LXC named `pfsense-hub-manager`, using Docker Compose to manage the application containers. Do not use Cloudflare Workers or Cloudflare hosting for this project.

### DEC-012, Frontend stack
**Status:** Accepted  
**Decision:** Use React with TypeScript and Vite for the web frontend.

### DEC-013, Backend separation
**Status:** Accepted  
**Decision:** Use a separate Node.js and TypeScript backend, exposing a REST API to the frontend. Keep firewall integration server-side and behind a provider/transport abstraction.

### DEC-014, Application database
**Status:** Accepted  
**Decision:** Use PostgreSQL as the application database, deployed as a dedicated service in the project's Docker Compose stack. Keep it on a private Compose network with a persistent data volume. Do not expose the database port publicly by default. Schema design, migrations, retention, backup/restore, and encryption requirements must be completed before production use.

### DEC-024, Per-site credential encryption and key provisioning
**Status:** Accepted  
**Decision:** Store each site's pfSense API credential encrypted in PostgreSQL using authenticated encryption, with AES-256-GCM as the implementation candidate pending review. Generate one high-entropy application encryption key automatically during installation. The installer must provide a recovery copy for the administrator to save in a password manager and install a separate runtime copy in a protected host-side location that the backend can read automatically. Normal operation and restarts must not require manual key entry. The key must never be stored in PostgreSQL, source control, browser storage, application logs, or API responses. Losing both the runtime key and recovery copy makes existing encrypted credentials unrecoverable. Back up the encrypted database and key separately. Define and test permissions, recovery, rotation, and Windows/Linux provisioning before production use.


### DEC-025, GUI-managed Hub access configuration
**Status:** Implemented on `feature/multi-site-onboarding` and merged to `main`; Linux/Tailscale path verified November 22, 2026
**Decision:** Provide access configuration in **Administration → Hub Settings**. A fresh installation binds the Hub UI to `127.0.0.1:8080` by default. The administrator can select one active method from LAN, Tailscale, or Custom; each tab retains its own endpoint values. Tailscale HTTPS uses the host's MagicDNS hostname, not its Tailscale IPv4 address, because the certificate identity is the MagicDNS name. LAN and Custom require an operator-managed trusted HTTPS reverse proxy forwarding to the assigned private host address on port 8080. The Linux Host Agent applies the supported host binding, verifies HTTPS, and rolls back on failure. For Tailscale it may create only the fixed private Serve proxy to `http://127.0.0.1:8080` when missing. Never mount the Docker socket into the web/API containers, never bind to `0.0.0.0` by default, and keep the API and PostgreSQL unpublished to external interfaces. The desired/applied endpoint revision and successful host-side probe are distinct from browser reachability.

### DEC-036, Local Linux development install mode
**Status:** Implemented and verified November 22, 2026
**Decision:** `scripts/install-linux.sh` supports two explicit installation modes and never switches modes implicitly. The default production mode stays privileged and pinned to a root-owned `/opt/pfsense-hub` checkout, because the Host Agent runs as root and executes Docker Compose against that checkout; a user-writable project directory would be a privilege-escalation path. `--local` (alias `--dev`) is an unprivileged development mode that runs from any checkout path, installs no Host Agent and no systemd unit, creates no root-owned files, and keeps `HUB_ACCESS_DEPLOYMENT_ENABLED=false`, so Hub access deployment remains disabled with the existing `503 HUB_ACCESS_DEPLOYMENT_DISABLED` response. Unknown arguments fail with usage instead of being ignored. Installing the privileged production mode at an arbitrary root-owned path remains out of scope and requires a separate decision. Local mode cannot verify or apply Tailscale or Custom Hub access deployment.

### DEC-037, Platform-complete dependency lockfile for source validation
**Status:** Implemented and verified on Linux, November 22, 2026
**Decision:** `package-lock.json` must record the platform-specific optional binary packages for every supported development platform, not only for the platform that generated it. npm records optional dependencies for the resolving platform (npm/cli#4828), so the previously committed lockfile, generated on Windows, contained no `@rollup/*` entries and only `@esbuild/win32-x64`. On Linux, `npm ci` then produced a tree where Rollup could not load its native binding and the API test suite aborted with `Cannot find module @rollup/rollup-linux-x64-gnu` before running any test. The lockfile is now generated with explicit platform overrides, which requires npm 11 or later: `npm install --package-lock-only --os=linux --os=win32 --cpu=x64 --libc=glibc --libc=musl`. This added 76 platform-specific entries and resolved four packages at patch level within their existing ranges (`rollup` and `@rollup/rollup-win32-x64-msvc` to 4.68.8, `fast-json-stringify` to 7.3.10, `caniuse-lite` to 1.0.30001827). Do not reintroduce per-environment binary repair steps: the `npm pack` workaround in `apps/web/Dockerfile` was removed, and the unreferenced `scripts/repair-rollup-linux.mjs` helper was deleted. Any lockfile regeneration requires the source validation suite (tests, typecheck, build) and a clean `npm ci` on Linux before commit. This decision affects dependency reproducibility only; it does not change runtime dependencies, product behavior, or the read-only security boundary.

### DEC-038, Identity-derived Host Agent trust policy and unprivileged development agent
**Status:** Implemented November 22, 2026
**Decision:** The restricted Host Agent derives trust from the identity that runs it instead of from a hard-coded `root` requirement, so GUI-managed Hub access deployment can be exercised from the developer's own checkout without `sudo`. The agent no longer exits when `geteuid() != 0`. Its configuration file, project directory, Compose file, and `.env` must instead be owned by the agent's effective UID/GID and must not be group/world writable, and `.env` must be mode `0600`. A root agent additionally still requires `/opt/pfsense-hub`, so a privileged agent can never be pointed at a user-writable tree; conversely an unprivileged agent cannot run against a root-owned checkout. Both mismatches fail closed. `socket_gid` (default `2000`) and `lock_path` (default `/run/pfsense-hub/deployment.lock`) are now validated configuration fields with production-preserving defaults, so existing `/etc/pfsense-hub/deployment-agent.json` files stay valid without a rewrite, and a new optional `--config PATH` argument selects a different configuration file, defaulting to `/etc/pfsense-hub/deployment-agent.json`. An unprivileged agent refuses a `socket_gid` it cannot grant (`AGENT_SOCKET_GROUP_REQUIRES_ROOT`) rather than silently widening socket access. `scripts/install-linux.sh --local --with-agent` provisions `~/.config/pfsense-hub/deployment-agent.json` owned by the installing account, atomically sets `HUB_DEPLOYMENT_AGENT_TOKEN` (generated once, never regenerated), `HUB_DEPLOYMENT_AGENT_SOCKET`, `HUB_AGENT_GID`, and `HUB_ACCESS_DEPLOYMENT_ENABLED=true` in the existing local `.env`, starts the agent through the new `scripts/dev-host-agent.sh` pidfile harness (no systemd unit, nothing written to `/etc` or `/opt`), recreates only the `api` container, and verifies socket ownership plus the bearer-authenticated API retrieval handshake. This adds no privilege: the account already owns the checkout, already runs the Compose project, and docker-group membership is already root-equivalent. Production behavior, the `/opt/pfsense-hub` pin, the systemd sandbox, the read-only API boundary, and the refusal of configuration-changing firewall operations are unchanged. Tailscale Serve still needs a one-time operator delegation (`sudo tailscale set --operator=<user>`); without it the agent fails closed with `HOST_OPERATION_FAILED` instead of falling back to an unsafe route.

### DEC-039, Host Agent monitoring and recovery operation surface
**Status:** Implemented and committed as `eb008f5`, November 22, 2026. Live-verified on the Ubuntu Docker host on November 23, 2026 for the read paths, bounded logs, Compose validation, the unauthenticated-denial boundary, and one whole-stack restart recorded against the `ahmed` actor; that operation's attribution is still to be confirmed by the operator. Still outstanding: an observed single-service `start`/`stop`/`restart` from the browser, the stack-stop recovery rehearsal from a host shell, and visual acceptance of the page against the approved mockup. See [System Monitoring & Recovery](SYSTEM-MONITORING-RECOVERY.md) sections 9 and 10, and [Verification and documentation closeout](VERIFICATION-AND-CLOSEOUT.md) sections 12 and 13.
**Decision:** System Monitoring & Recovery (DEC-026, DEC-027) is implemented through the existing restricted Host Agent rather than a new privileged path. At protocol version 2 the agent requires an explicit `operation` field and supports `system.status`, `system.logs`, `compose.validate`, `system.operation`, and `system.operationResult`; requests are strict objects, so unknown operations, actions, targets, or extra keys are rejected instead of forwarded. `system.operation` accepts only `start`, `stop`, and `restart` for `web`, `api`, and `db`, or `stack` for those three services. Each pair maps to fixed argv with the target interpolated only after allowlist validation, so no caller can supply a Compose argument, flag, profile, container name, project path, or shell fragment. The code-server container, volume deletion, image update or rebuild, command-prompt execution, and arbitrary host administration remain out of scope. Operations are exactly-once by manager-assigned UUID: the manager journals the row and its `system.operation.request` audit event before dispatch, the agent persists the id before answering `accepted`, a retried id is not re-executed, and a reused id with a different action or target is refused with `OPERATION_CONFLICT`. The host journal is `operation_state_path`, defaulting to `host-operations.json` beside `lock_path` (`/run/pfsense-hub/host-operations.json` for the systemd unit, inside `ReadWritePaths` and cleared on reboot; the checkout's `run/host-agent/` for the unprivileged development agent). It is written atomically with mode `0600`, rejects symlinks, foreign owners, malformed envelopes, and unknown entry shapes, prunes settled entries while retaining unsettled ones, and fails closed rather than inferring an outcome. Dispatch answers before execution and the worker takes the same `flock` as `deployment.apply`, so a slow Compose action does not block read-only monitoring. Command completion is not recovery: the agent verifies container state through `docker compose ps` and reports `OPERATION_UNVERIFIED` unless every addressed service reaches the requested state, and the manager sets `verified_at` only from a verified result. Reconciliation settles a row as `unknown` on timeout or when the agent no longer holds the id, and leaves the row untouched while the agent is unreachable instead of inventing an outcome. Both capabilities stay fail-closed behind `HUB_HOST_MONITORING_ENABLED` and `HUB_HOST_OPERATIONS_ENABLED` (the latter requires the former), with `HUB_HOST_OPERATION_TIMEOUT_MS` bounding reconciliation, and every mutation route stays administrator-only and audited. This decision adds no Docker socket to the web or API containers, no arbitrary command execution, and no pfSense configuration change.

### DEC-042, Site telemetry from the eight approved read-only endpoints

**Status:** Implemented November 23, 2026

**Decision:** The site workspace pages Overview, Monitoring, Interfaces, Gateways, Services, and Compatibility read live data from one sanitized contract, `GET /api/v1/devices/:deviceId/snapshot`, instead of illustrative fixtures. The endpoint performs the existing fixed eight-operation collection (`status/system`, `status/gateways`, `status/interfaces`, `status/services`, `system/version`, `diagnostics/arp_table`, `firewall/states`, `firewall/states/size`) and adds no upstream route, HTTP method, firewall permission, or caller-controlled destination. The pre-existing `GET /api/v1/devices/:deviceId/overview` path is retained as an alias of the same handler so a second collection path cannot diverge.

The manager never forwards a firewall payload. `apps/api/src/pfsense/observations.ts` validates each response with a narrow schema and constructs an explicit allowlisted object, so serial numbers, Netgate IDs, MAC addresses, hardware interface names, monitor and source IP addresses, and packet/byte counters are not modeled at all. ARP and state-table responses contribute counts and limits only; no entry is persisted, returned, or logged.

Compatibility metadata is persisted by migration `016_device_compatibility.sql` (`release`, `platform`, `api_package_version`, `compatibility`, `compatibility_checked_at`) and appears in the device inventory. `api_package_version` remains `null` and CPU architecture remains unreported because no approved endpoint exposes either; they are not inferred. A compatibility verdict of `mismatch` is recorded only when the firewall's own release/platform string contradicts the edition declared in the site profile, and the page asks the administrator to correct the profile; the manager does not change firewall configuration.

Capability state is derived from each device's own recorded `poll_runs`. A successful operation reports `supported: true`. Only `unsupported`, `authorization`, and `authentication` failures report `supported: false`, because those are the only classes that establish the firewall refused or lacks the operation. Transport, TLS, rate-limit, and schema failures report `supported: null` with a failed verification, and a device with no polling history reports `unverified` rather than `supported`. `poll_runs.operation_group` now records one label per operation (`arpTable` replaces the shared `diagnostics` label); capability derivation falls back to the historical labels for rows written before this decision.

The server caches a snapshot in process for 10 seconds (success) or 2 seconds (partial/unavailable), configured by `PFSENSE_OBSERVATION_CACHE_MS` and `PFSENSE_OBSERVATION_ERROR_CACHE_MS`, with single-flight per device and a 64-device bound. Successful results are evicted when a device's profile, credential, TLS trust, or enabled state changes, or when it is archived. Nothing is persisted across restarts. The browser uses the same 10-second window and single-flight behavior, so navigating Overview → Monitoring → Interfaces → Gateways → Services → Compatibility performs one snapshot request and one eight-operation collection.

**Explicitly not added:** CPU or memory history and trend charts (the API returns a point-in-time sample), utilization alerts (no approved thresholds), a claimed REST API package version or CPU architecture, any write operation, any state-changing firewall action, and any change to the eight-endpoint firewall-side permission scope. Rules, Aliases, NAT, Routing, DHCP, DNS, Certificates, and VPN remain explicitly labeled preview fixtures because no approved endpoint supplies their data.

**Verification:** API typecheck, web typecheck, and production build pass; the API suite reports 314 passed tests, including new sanitization, cache, capability, and route-boundary tests. Migration `016_device_compatibility.sql` applied on the running development stack, the API restarted healthy, and the new routes reject unauthenticated requests with `401 AUTHENTICATION_REQUIRED`. A live authenticated session then produced a full snapshot of the registered firewall: all eight operations recorded `success`, no poll alert was raised, and the inventory reports `release` `26.07.2-RELEASE`, `platform` `Netgate 2100`, `compatibility` `verified`. That session also exposed one defect — the compatibility queries selected `device_id` from `managed_devices`, whose key is `id`, so `GET /api/v1/devices` returned `500` and the site list failed to load. The projection is now `id AS device_id`, the SQL was re-run against the live database before rebuilding, and the repository tests pin the projection.

### DEC-043, Background polling scheduler and poll-history retention
**Status:** Approved and implemented November 23, 2026. Opt-in via `PFSENSE_POLLING_ENABLED` (default `false`). Not yet enabled on any running installation and not live-verified against a firewall. Parameters P-1 to P-10 are recorded in [Background Polling Design](BACKGROUND-POLLING-DESIGN.md) section 2; this decision supersedes the "polling frequency remains open" statement in `docs/PRD.md` FR-4, narrows open question 8 there to the tables other than `poll_runs`, and closes the roadmap note that continuous monitoring must not be claimed before a scheduler exists.
**Decision:** Per-device monitoring is produced by a scheduler inside the API process that decides *when* the existing collection runs and nothing more. It calls the same `PfSenseProvider.collect(deviceId, pollObserver(deviceId))` path as the site snapshot route, so the eight-operation allowlist, the fixed upstream routes, the per-operation `poll_runs` rows, the `pfsense_poll_*` metrics, and the shared `recordPollHealth` behavior are identical for scheduled and page-triggered polls. No new endpoint, upstream route, or firewall permission was requested, and the read-only boundary is unchanged: the scheduler never sends a write, an apply, a command, or a caller-supplied destination.

Approved parameters: 60 s interval per enabled non-demo device; fleet concurrency of 2 devices; random 0-15 s jitter on a device's first sighting and on each scheduled success; retry backoff of 30/60/120/300 s with the 300 s cap, reset on a fully successful collection, and floored at the configured interval so a failing device is never polled more often than a healthy one; 30-day `poll_runs` retention pruned in bounded 5,000-row batches at startup and every 24 h; alert on the first failed collection using the existing `device-poll:<deviceId>` dedup key, auto-resolved on the first fully successful collection; single scheduler per API process, started after migrations and listen and stopped on shutdown, with no leader election; and cache write-through for one interval (capped at 600 s), while a failed collection keeps the 2 s failure window.

The schedule itself is memory-only (`nextAttemptAt`, `consecutiveFailures` per device) and is re-derived from `managed_devices` after a restart, so there is no new migration and no scheduling state to corrupt. Disabled, archived, and demo devices are dropped from the schedule without a restart. Each device is collected inside its own error boundary, so one timeout, schema rejection, or thrown error cannot delay another device or abort the cycle; thrown errors are logged with the device ID and error class only, never the message. A retention deletion is audited as `polling.history_pruned` with the row count, an empty prune writes nothing, and a prune failure is logged and ignored rather than stopping monitoring.

**Explicitly not added:** any write, apply, reboot, or configuration-changing firewall operation; notification delivery; utilization thresholds or trend charts; multi-instance leader election or a job queue; a second health or retention code path; any change to the eight-endpoint firewall permission scope.

**Known constraint:** a second API replica must not also schedule. The current deployment runs exactly one `api` container; a future horizontal scale-out needs its own decision, because two schedulers would double collection and duplicate `poll_runs` growth while the alert dedup key would hide the duplication.

**Verification:** 21 new tests across `poll-scheduler.test.ts` (14), `poll-retention.test.ts` (4), and the cache write-through cases in `observation-cache.test.ts` (3): cadence and jitter boundaries, the `[30s, 60s, 120s, 300s, 300s]` backoff sequence and reset, per-device isolation, the concurrency bound, disabled/demo exclusion, shared health input, overlap skipping, timer start/stop, retention scope and bounds. The API suite reports 27 files / 335 tests passed; API and web typecheck pass; the production build passes with unchanged web hashes. The rebuilt `api` container runs with `PFSENSE_POLLING_ENABLED=false`, is healthy, and logs no scheduler start line, confirming the disabled path is inert in deployment. The same container was then recreated with `PFSENSE_POLLING_ENABLED=true`, and the scheduler logged its start line and completed eight consecutive scheduled cycles of all eight operations at 70–79 s spacing with no page request, no new alert, and no `warn`/`error` log line (closeout section 16). A `yes` value is refused at startup rather than read as `false`.

**Live behaviour verification, November 23, 2026.** The three paths this decision left unproven were drilled against the registered Plus firewall in the same deployment, with no application change and no firewall write (closeout section 19). A read inside the interval returned `meta.cacheHit: true` with `durationMs: 0` and no new `poll_runs` row, both from a route-served entry and 52 s after a scheduled write-through; because only the scheduler stores with `min(intervalMs, 600 s)`, the 52 s read could only be served from the write-through entry, while the route-side miss stored for the 10 s collection window and expired. Two consecutive failed collections produced exactly one `device-poll:<deviceId>` alert with `occurrence_count` 1 → 2 and auto-resolved it on the next fully successful cycle, recording `alert.auto_resolve` with `resolvedCount: 1`. Lowering `retentionDays` through the settings save pruned 40 aged rows, audited `polling.history_pruned {removedRuns: 40}`, and re-armed the scheduler in process; a zero-row prune wrote nothing. One constraint on how this decision can be evidenced was found and is recorded rather than glossed over: because a failure sets `nextAttemptAt = now + max(step, intervalMs)`, at the default 60 s interval the first two retries land at exactly 60 s and only a third consecutive failure reaches 120 s, so a two-failure drill cannot demonstrate the widening sequence — the `[30/60/120/300]` steps remain covered by `poll-scheduler.test.ts` at a 15 s interval. Not exercised: a prune batch at the 5,000-row limit, the 24 h repeat timer, failure classes other than TLS, fleet concurrency above one device, and the browser form submission for the cadence save.

### DEC-044, Runtime polling settings in Hub Settings

**Status:** Approved and implemented, November 23, 2026, on the operator's instruction to move as much non-security configuration out of `.env` as can be done without weakening a control. Proposal and rationale: [RUNTIME-SETTINGS-PROPOSAL.md](RUNTIME-SETTINGS-PROPOSAL.md).

**Decision:** Exactly four background-polling parameters become editable in **Administration → Hub Settings**: the poll interval, concurrency, jitter, and `poll_runs` retention. They are bounded integers the scheduler already validated, they grant no capability, reveal no secret, and change no upstream route or firewall permission. Editing them no longer requires editing a file on the host and recreating the API container.

**Single source: the Hub database.** Migration `017_hub_polling_settings.sql` creates a singleton `hub_polling_settings` row (`id = 1`) with `CHECK` constraints mirroring the scheduler bounds, a `jitter_ms < interval_ms` constraint, and `updated_by uuid REFERENCES admin_users(id) ON DELETE SET NULL`; migration `018_seed_hub_polling_settings.sql` seeds it with the install values (`60000` ms, `2` devices, `15000` ms jitter, `30` days). A new migration was used rather than editing `017` because applied migrations keep a checksum the API verifies at boot. The row is the only source of these four numbers. `PFSENSE_POLLING_INTERVAL_MS`, `PFSENSE_POLLING_CONCURRENCY`, `PFSENSE_POLLING_JITTER_MS`, and `PFSENSE_POLLING_RETENTION_DAYS` were removed from `config.ts`, from `.env.example`, from the `.env` that `scripts/install-linux.sh` generates, and from the running deployment's `.env`; there is no environment default, no fallback, and no second value that can disagree with what the scheduler is running. `GET` reports `source: "install"` while `saved_at` is NULL (the seeded values, untouched) and `source: "hub"` once an administrator saves, with `updatedAt` and `updatedBy`. `saved_at` is its own column, added by `019_hub_polling_settings_saved_at.sql`, rather than something inferred from attribution, because a cadence an administrator saved must not look untouched after that account is retired. If the row is ever missing — a hand-deleted row, or a database restored from before `018` — or if it no longer satisfies the bounds (only reachable by editing the table outside the manager), the API rewrites it to the install values and reports `source: "install"`, so the API and the panel always describe the cadence that is actually running. The scheduler's constructor keeps its own assertions; the database CHECKs and the route validation are defence in depth, not the only guard.

This is the standard shape for runtime configuration in this product: `.env` carries secrets, database credentials, port and bind wiring, and fail-closed feature gates; anything an administrator tunes at runtime lives in the Hub database and is edited in Hub Settings. DEC-041 retired the old Hub-wide Application Settings page for the same reason, and this decision continues in that direction rather than adding environment variables back.

**API.** `GET` and `PUT /api/v1/hub-settings/polling`, both administrator-only, enforced in the route module and again by the server's admin-only hook so a future route registration cannot silently widen access. `PUT` accepts only the four integers (`strict`), rejects out-of-range and fractional values and `jitter >= interval` with `400 INVALID_POLLING_SETTINGS`, persists `outcome: "success"`/`"failure"` audit events as `hub.settings.update` with `targetType: "hub_polling_settings"` and the previous and updated integers, and never includes credentials, device data, or host paths. Audit metadata stays bounded by the existing sanitiser.

**Runtime application.** A save constructs the replacement `PollScheduler` *before* stopping the running one, then swaps and starts; a value the scheduler refuses therefore leaves the previous cadence running, and two schedulers never overlap. If the row cannot be persisted, the previous cadence is restored and the request fails with `500 POLLING_SETTINGS_NOT_SAVED`, so runtime and storage cannot silently diverge. An in-flight cycle finishes; the new interval governs the next one. Retention changes take effect at the next prune; concurrency changes apply to subsequent cycles.

**Answers to the proposal's four open questions.** (1) No fleet-wide pause was added: per-site `enabled` remains the pause mechanism (DEC-031), and `PFSENSE_POLLING_ENABLED` stays environment-only because whether a process may schedule at all is a deployment decision and the single-scheduler constraint (DEC-043) must not be flippable from a browser. (2) The precedence question was answered by superseding it. The proposal offered "environment is the default and fallback, the stored row is the override"; the operator rejected that two-source model and instructed that runtime settings live in the Hub, with `.env` kept for a clean install. The row is therefore the only source, seeded by the migration, and clearing a saved value is no longer a rollback to environment values — the administrator edits the value in Hub Settings, where it is visible and audited. (3) No separate default-off flag: the only privileged surface is an integer row the scheduler already validates, the write is administrator-only and audited, and a second gate would add a configuration state where the form appears broken; the flag requirement in DEC-036 exists for privileged host-agent deployment, a different risk. (4) `GET` is administrator-only as well: this is Hub configuration, not site observation, and the whole `/api/v1/hub-settings/polling` namespace keeps one authorization rule.

**Explicitly not moved.** Secrets and key paths (`PFSENSE_API_KEY_FILE`, `APP_ENCRYPTION_KEY_FILE`, `HUB_DEPLOYMENT_AGENT_TOKEN`); fail-closed host gates (`HUB_ACCESS_DEPLOYMENT_ENABLED`, `HUB_HOST_MONITORING_ENABLED`, `HUB_HOST_OPERATIONS_ENABLED`, `HUB_HOST_OPERATION_TIMEOUT_MS`); infrastructure read before the database is reachable (`DATABASE_URL`, `POSTGRES_*`, `COMPOSE_PROJECT_NAME`, `HUB_BIND_ADDRESS`, `WEB_PORT`, `HUB_AGENT_API_PORT`, `HUB_AGENT_GID`, `HUB_DEPLOYMENT_AGENT_SOCKET`); per-device identity, TLS trust, and credentials, which are GUI-managed on the device profile; `PFSENSE_API_TIMEOUT_MS`, better expressed per device than Hub-wide; the observation-cache lifetimes, performance tuning with no operator value; and the legacy single-firewall bootstrap keys, which stay supported in code until an intentional migration retires them. `.env.example` no longer documents the four polling values: it states that the cadence lives in the Hub database and that the installer seeds it, and `scripts/install-linux.sh` writes a `.env` containing only the process-level `PFSENSE_POLLING_ENABLED` gate.

**Explicitly not added:** no new upstream route, firewall endpoint, or permission; no write, apply, reboot, or command operation; no schedule persistence beyond the four integers; no relaxation of the single-scheduler rule or the read-only boundary.

**Verification:** 17 tests in `hub-polling-settings.test.ts` cover the bounds (including both endpoints of every range), the `jitter < interval` rule, unknown and fractional keys, creation of the install row when it is missing, `source: "install"` versus `"hub"` including a saved cadence whose author is no longer attributed, an out-of-bounds row repaired to the defaults, `401`/`403` for both methods, the applied-and-audited save, the stored-but-not-applied save with `PFSENSE_POLLING_ENABLED=false`, rejection before any scheduler or database contact, and both failure recoveries. ### DEC-045, Administrator accounts are deactivated, never deleted

**Status:** Approved, November 23, 2026, on the operator's instruction to settle the account-removal question that DEC-044 verification raised.

**Decision:** An administrator who should no longer have access is deactivated (`is_active = false`), its stored credential is replaced with a value that cannot verify, and its sessions are deleted. That three-step retirement is the documented removal procedure (closeout section 17). There is no delete path for `admin_users`: no API route deletes a row, the procedure does not delete one, and none is planned as cleanup. The append-only audit trail is the authoritative record of what an identity did, and it keeps both `actor_id` and the username snapshot on each event, so the history stays readable after the account is retired.

**Why deletion does not work today.** `audit_events.actor_id` is declared `REFERENCES admin_users(id) ON DELETE SET NULL`, but migration `004_user_audit_alerts.sql` installs `audit_events_no_update`, a `BEFORE UPDATE OR DELETE` trigger whose function raises `audit_events are append-only`. The `SET NULL` the FK promises is an `UPDATE` on an audit row, so the trigger aborts it. Observed, not inferred: `DELETE FROM admin_users WHERE username = 'dec044-verify'` — an account with 7 audit rows — failed with `ERROR: audit_events are append-only` and the server printed the offending statement as `UPDATE ONLY "public"."audit_events" SET "actor_id" = NULL`. An administrator who has ever signed in therefore cannot be deleted at all.

**Rejected alternatives.** Disabling the guard for `actor_id` alone, or dropping the FK so an event may point at a missing user: both weaken the append-only property that makes the trail trustworthy, and only to tidy a user list. `ON DELETE CASCADE` on `actor_id`: destroys audit history, which the product constraints forbid. Keeping only a username snapshot with no FK: sound in principle, but it is a schema change touching every audit query and belongs to the feature that needs it rather than to account cleanup.

**Not decided here.** Any hard-delete, erasure, or anonymisation feature — a compliance request, for example — needs its own record: the exact schema change, a migration, which structural audit facts are retained, approval, and tests proving the trail cannot be rewritten. Until such a record exists, the answer to "delete this administrator" is deactivation.

**Verification:** observed on the deployment. `dec044-verify` is `is_active = false` with an unusable stored credential and 0 sessions; a login attempt returns `401`, and a session cookie issued before retirement returns `401`; `hub_polling_settings` attribution was cleared to the same NULL state a retirement leaves, and the saved cadence still reported `source: "hub"` (closeout section 17). No code changed for this decision: no route deletes administrators, and the retirement is an operator procedure recorded in that section, not a feature.

### DEC-046, Collection limits in Hub Settings

**Status:** Approved and implemented, November 23, 2026, on the operator's instruction to move the last environment-variable tuning knobs into the Hub and remove them from `.env`. This record supersedes the paragraph in [RUNTIME-SETTINGS-PROPOSAL.md](RUNTIME-SETTINGS-PROPOSAL.md) section 3 that kept these three values out of scope.

**Decision:** Three integers become editable at **Administration → Hub Settings → Collection limits**: the upstream read timeout, the successful-observation reuse window, and the failed-observation reuse window. They are stored in a singleton `hub_collection_settings` row (`id = 1`), created and seeded by `020_hub_collection_settings.sql` with the values the retired environment variables defaulted to — `10000` ms timeout, `10000` ms success reuse, `2000` ms failure reuse.

**Single source: the Hub database,** exactly as DEC-044 settled for the polling cadence. `PFSENSE_API_TIMEOUT_MS`, `PFSENSE_OBSERVATION_CACHE_MS`, and `PFSENSE_OBSERVATION_ERROR_CACHE_MS` were removed from `config.ts`, `.env.example`, `compose.yaml`, the `.env` that `scripts/install-linux.sh` generates, and the running deployment's `.env`. **Bounds, enforced three times over.** `requestTimeoutMs` and `successCacheTtlMs` are 1000–60000 ms, `failureCacheTtlMs` is 0–60000 ms, and `failureCacheTtlMs` may not exceed `successCacheTtlMs`; the API schema (`collectionSettingsSchema` in `hub-settings.ts`), the table `CHECK` constraints, and `CollectionLimits.apply` each enforce the same rules. The upper bound on the failure window matters operationally: it keeps the "reuse a failed observation" shortcut short, so a recovering firewall is noticed quickly.

**Why these three and no others.** They are the remaining bounded integers with no capability, no secret, no host binding, and no security meaning: a timeout and two cache lifetimes. A cache lifetime cannot widen the eight-operation allowlist, redirect a device, disable certificate verification, or send a write, which is what keeps this inside the read-only boundary.

**API.** `GET` and `PUT /api/v1/hub-settings/collection`, both administrator-only in the route module and again in the server's admin-only path list, so a later route registration cannot silently widen access. The `PUT` body is a strict object accepting only the three integers; out-of-range, fractional, unknown, or `failureCacheTtlMs > successCacheTtlMs` input returns `400 INVALID_COLLECTION_SETTINGS`. The response is `{ requestTimeoutMs, successCacheTtlMs, failureCacheTtlMs, source, updatedAt, updatedBy }`, and `PUT` adds `applied`.

**Runtime application, without a restart.** `DevicePfSenseClientFactory` builds a short-lived client per operation and reads the `CollectionLimits` holder when it does, so a new timeout governs the next upstream request; `ObservationCache.setTtls` takes the new windows on the next stored entry and keeps its single-flight, size, and device bounds; the poll scheduler is rebuilt after a save so the failure window it seeded is current. The save applies the values to the running process *before* persisting them: a value the runtime refuses returns `500 COLLECTION_SETTINGS_NOT_APPLIED` with the previous values still in effect and no row written, and a failed write restores the previous values and returns `500 COLLECTION_SETTINGS_NOT_SAVED`. An in-flight collection finishes with the values it started with.

**Audit.** One `hub.settings.update` event per save that reaches the runtime: `targetType: "hub_collection_settings"`, outcome `success` or `failure`, metadata carrying the previous and updated integers and `applied`. No credentials, device data, or host paths. Schema rejections return `400` without an event because no state changed; authentication and authorization denials are audited by the server's response hook.

**Explicitly still environment-only,** for the reasons recorded in DEC-044: the fail-closed host gates (`HUB_ACCESS_DEPLOYMENT_ENABLED`, `HUB_HOST_MONITORING_ENABLED`, `HUB_HOST_OPERATIONS_ENABLED`, `HUB_HOST_OPERATION_TIMEOUT_MS`); Host Agent wiring and its token (`HUB_DEPLOYMENT_AGENT_SOCKET`, `HUB_DEPLOYMENT_AGENT_TOKEN`, `HUB_DEPLOYMENT_AGENT_API_PORT`, `HUB_AGENT_GID`); infrastructure read before the database is reachable (`DATABASE_URL`, `POSTGRES_*`, `COMPOSE_PROJECT_NAME`, `HUB_BIND_ADDRESS`, `WEB_PORT`); the Compose file-secret paths (`PFSENSE_API_KEY_FILE`, `APP_ENCRYPTION_KEY_FILE`); the `PFSENSE_POLLING_ENABLED` process gate; and the legacy single-firewall bootstrap keys, which stay supported in code until an intentional migration retires them.

**Explicitly not added:** no new upstream route, firewall endpoint, or permission; no write, apply, reboot, or command operation; no per-device timeout override. A Hub-wide timeout cannot express a slow site, and moving the value onto the device profile would need a `managed_devices` migration, a per-device UI, and its own decision; that remains an open design question, not a decided feature.

**Verification:** `hub-collection-settings.test.ts` adds 15 tests — the resolution path (install row, saved row, missing row, out-of-bounds row repaired, `source` derived from the marker) and the route path (`401`/`403`, `400` on each bound and on `failure > success`, the applied-and-audited save, the runtime refusal, the storage failure restoring the previous values). `observation-cache.test.ts` pins that `setTtls` governs later entries and refuses out-of-bounds values; `device-client-factory.test.ts` pins that the stored timeout reaches the client instead of the install default; `config.test.ts` pins that the retired variables are ignored. The API suite reports 29 files / 371 tests passed, and API and web typecheck pass. On the live Compose deployment migration `020` applied, `hub_collection_settings` held `1 | 10000 | 10000 | 2000`, and the `api` container's environment carries none of the three retired variables. A save clicked in **Hub Settings** returned "Collection limits applied. Not measured: a live change in timeout or cache reuse, because the saved values were the install values and no behavioural difference was observable; that path is covered by the tests above and by the `applied` flag the route returns.

### DEC-047, Page-scoped configuration reads start with Aliases

**Status:** Approved and implemented (manager side), November 23, 2026, continuing the operator's instruction to build the complete frontend surface with real data wherever the read-only boundary allows it. Runtime verification against a firewall is **pending** and is not claimed.

**Decision:** Firewall configuration may be read through a second, fixed upstream allowlist that is separate from the eight polled status operations. The first and only member is `GET /api/v2/firewall/aliases` (privilege `api-v2-firewall-aliases-get`), exposed by the manager as `GET /api/v1/devices/:deviceId/configuration/aliases`. The Aliases site page now renders that data instead of preview fixtures.

**Why a second allowlist instead of adding to the eight.** The eight operations are a *health-collection* contract: the snapshot calls all of them on every poll, writes one `poll_runs` row each, feeds the capability matrix, metrics, alerting, and retention. A configuration page is viewed on demand and must not (a) multiply upstream load on every poll, (b) create `poll_runs` evidence that could flip a capability verdict, or (c) inherit the polling cache window. `configurationRoutes` in `client.ts` is therefore a distinct `as const` map with its own type, its own `getConfiguration` method, and its own cache in `server.ts`; `pfSenseOperations` is unchanged, and a test pins that `aliases` is absent from it. The two maps share one request path, so timeout, TLS pinning, redirect rejection, the 2 MB response cap, envelope validation, and error classification cannot diverge between them.

**Still no arbitrary proxy.** The browser calls a manager route; the device is resolved from `managed_devices`; the upstream path is a compile-time constant. No caller-supplied URL, path, method, header, or body exists, and the route accepts GET only. Adding an entry to `configurationRoutes` is a product and security decision that requires this record to be amended, exactly like the eight-operation list.

**Authorization: administrator-only.** Unlike the eight telemetry operations, aliases describe how the firewall is configured rather than how it is behaving. The server's admin-only path list therefore matches `/api/v1/devices/*/configuration/*`, so an authenticated non-administrator is refused with `403` at the server boundary instead of relying on the frontend to hide the page. This is the deny-by-default position; extending the read to the `user` role would require its own decision plus a role/device capability check.


**Sanitization and bounds, in `configuration.ts`.** Only `name`, `type`, `descr` → `description`, and `address` → `entries` are retained. `id`, `detail`, `tracker`, and any undocumented field are dropped by construction, not by deletion. Control characters are replaced, values are length-capped (31 / 200 / 256), non-string addresses are ignored rather than coerced, and a `type` outside `host | network | port` becomes `null` instead of being guessed. At most 2,000 aliases and 200 entries per alias are retained; `entryCount` still reports the firewall's own count and `truncated` / `entriesTruncated` mark what was withheld, so the page never implies it is showing everything. A `data` value that is not an array of objects raises `ConfigurationShapeError` and the route answers `FIREWALL_INVALID_RESPONSE` — a malformed body is never partially displayed.

**Error translation.** Manager-owned codes, so the browser never sees an upstream message: `FIREWALL_PERMISSION_DENIED` (502, names the privilege to grant), `FIREWALL_ENDPOINT_UNSUPPORTED` (502, names the route), `FIREWALL_TIMEOUT` (504), `FIREWALL_INVALID_RESPONSE` (502), `FIREWALL_UNAVAILABLE` (502, authentication/TLS/rate-limit/transport). Upstream refusals are reported as `502` rather than the upstream `403`/`404` because the caller's own authorization succeeded and the manager's 403 is reserved for `ADMINISTRATOR_REQUIRED`; collapsing the two would make a missing firewall privilege look like a manager permission problem. Device-state rules are the same as other device routes: `400 INVALID_DEVICE_ID`, `404 DEVICE_NOT_FOUND` for unknown and demo records alike, `409 DEVICE_DISABLED`, `409 DEVICE_UNAVAILABLE` if the profile disappears between the check and the client build. The frontend renders permission and unsupported refusals as warnings rather than hard errors, because both mean "not verified for this device", not "the manager is broken".

**Caching.** 60 s success / 10 s failure per device, single-flight, 64 devices, `ObservationCache` with the same bounds as the observation cache, invalidated when the device profile changes. The short failure window keeps a just-granted privilege visible within seconds. The client is closed on both success and failure.

**What this decision does not do.** No write, apply, delete, or command operation; `PUT` and `DELETE` on the same path remain prohibited. No new endpoint was granted on any firewall by this decision. No configuration data is persisted: the read model exists only in memory, and there is no audit event for a read beyond the existing request logging, matching how the snapshot reads are handled. No polling, alerting, metric, or retention change: these reads bypass `poll_runs` and the device health metrics entirely. Other configuration areas are not covered; each needs its own verified route and its own amendment.

**Pending, explicitly.** The `pfsense_hub` account still holds only the eight status GET privileges. The first live call will therefore return `FIREWALL_PERMISSION_DENIED` until an operator (1) confirms `GET /api/v2/firewall/aliases` and its response schema on the installed REST API package for that firewall, (2) grants exactly `api-v2-firewall-aliases-get` to `pfsense_hub`, (3) tests both allowed and denied access, and (4) records the package version, release, architecture, result, and rollback in INTEGRATION-STATUS.md. Until then the page is implemented but unverified, and the UI says so through the error it receives rather than by pretending the read succeeded.
